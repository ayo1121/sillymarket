## Identified Vulnerabilities

### ISSUE #1: Error Messages May Expose Sensitive Information

**RISK:** MEDIUM  
**LOCATION:** Multiple components (MarketDetails.tsx, BettingModal.tsx, CreateMarket.tsx, AdminPanel.tsx)

**Description:**  
Error messages from backend API calls and Solana transactions are displayed directly to users without sanitization. While React escapes HTML, error messages may contain:
- Internal file paths
- Stack traces
- Database query details
- Wallet addresses
- Transaction details that could aid attackers

**Current Code (MarketDetails.tsx:637-644):**
```typescript
} catch (error: any) {
  console.error("Resolve error:", error);
  const errorMsg = error?.message || "Failed to resolve market";
  if (errorMsg.includes("Unauthorized") || errorMsg.includes("InvalidState")) {
    toast.error("Cannot resolve: " + errorMsg);
  } else {
    toast.error(errorMsg);  // ← Raw error message shown to user
  }
}
```

**Current Code (BettingModal.tsx:similar pattern):**
```typescript
} catch (error: any) {
  console.error("[BettingModal] placeBet error", error);
  toast.error(error?.message || "Failed to place bet");  // ← Raw error
}
```

**PATCH:**

Create a safe error handler utility:

```typescript
// client/web/src/lib/errorHandling.ts

/**
 * Sanitize error messages for user display
 * Removes sensitive information while preserving useful context
 */
export function sanitizeErrorMessage(error: any): string {
  if (!error) return "An unknown error occurred";
  
  const rawMessage = error?.message || error?.toString() || "Unknown error";
  
  // Known safe error patterns from Anchor/Solana
  const safePatterns = [
    /Unauthorized/i,
    /InvalidState/i,
    /AlreadyResolved/i,
    /AlreadyClaimed/i,
    /BettingClosed/i,
    /InsufficientFunds/i,
    /BadParam/i,
    /NotClaimed/i,
    /Overflow/i,
    /User rejected/i,
    /Transaction simulation failed/i,
  ];
  
  // Check if error matches known safe patterns
  for (const pattern of safePatterns) {
    if (pattern.test(rawMessage)) {
      return rawMessage;
    }
  }
  
  // For unknown errors, return generic message
  // Log full error for debugging
  console.error("[ErrorHandler] Sanitized error:", rawMessage);
  
  return "An error occurred. Please try again or contact support.";
}

/**
 * Safe error toast helper
 */
export function showErrorToast(error: any, fallbackMessage?: string) {
  const message = sanitizeErrorMessage(error);
  toast.error(fallbackMessage ? `${fallbackMessage}: ${message}` : message);
}
```

**Usage:**
```typescript
// Replace all error handling with:
import { showErrorToast } from "@/lib/errorHandling";

try {
  // ... transaction code
} catch (error: any) {
  console.error("Full error:", error);  // Still log for debugging
  showErrorToast(error, "Failed to resolve market");
}
```

### ISSUE #2: Client-Side Authorization Checks Without Backend Enforcement

**RISK:** MEDIUM  
**LOCATION:** MarketDetails.tsx (lines 576-709), AdminPanel.tsx (lines 360-370)

**Description:**  
The frontend uses `canResolveMarket()` and `canClaimPosition()` helper functions to show/hide UI elements (resolve buttons, claim buttons). However, these are **UI-only checks** and don't enforce security.

**Problem:**  
- An attacker can modify the frontend code to bypass these checks
- The UI might show "you can't resolve" but an attacker could still call the transaction directly
- This creates a false sense of security

**Current Code (MarketDetails.tsx:576-593):**
```typescript
{publicKey && market && (() => {
  const canResolve = canResolveMarket({
    market: market.rawAccount,
    wallet: publicKey,
    configAuthority,
    configAdminPreCutoff: config?.adminPreCutoff ?? false,
  });

  return (
    <>
      {canResolve && (
        <div className="win95-window bg-background p-1">
          {/* Resolve UI shown only if canResolve is true */}
        </div>
      )}
    </>
  );
})()}
```

**Analysis:**  
✅ **GOOD NEWS:** The on-chain program (`programs/yesno_markets/src/lib.rs`) **DOES** enforce authorization:
- `resolve` instruction (lines 416-529) checks `market.creator` or `config.authority`
- `claim_winnings` instruction (lines 566-625) checks `position.owner`

❌ **ISSUE:** The frontend logic is redundant and could mislead developers into thinking it provides security.

**PATCH:**

Add clear comments and improve error handling:

```typescript
// client/web/src/pages/MarketDetails.tsx

{publicKey && market && (() => {
  // UI-ONLY CHECK: This is for UX, not security
  // The on-chain program enforces actual authorization
  const canResolve = canResolveMarket({
    market: market.rawAccount,
    wallet: publicKey,
    configAuthority,
    configAdminPreCutoff: config?.adminPreCutoff ?? false,
  });

  // SECURITY NOTE: Even if we hide the button, users can still
  // attempt to call resolveMarket() directly. The Anchor program
  // will reject unauthorized attempts with "Unauthorized" error.

  return (
    <>
      {canResolve && (
        <div className="win95-window bg-background p-1">
          <div className="bg-primary text-primary-foreground px-2 sm:px-3 py-2 mb-1">
            <span className="font-black text-xs sm:text-sm tracking-tight">resolve market</span>
          </div>
          <div className="win95-sunken bg-background p-3 sm:p-4 space-y-2">
            {/* ... resolve UI ... */}
          </div>
        </div>
      )}
      
      {/* Show informative message if user can't resolve */}
      {!canResolve && market.state === "open" && (
        <div className="win95-window bg-background p-1">
          <div className="win95-sunken bg-background p-3 text-xs text-muted-foreground">
            Only the market creator (after cutoff) or admin can resolve this market.
          </div>
        </div>
      )}
    </>
  );
})()}
```

**Recommendation:**  
Document in code that:
1. UI checks are for **UX only**
2. **On-chain program** is the source of truth for authorization
3. Always handle "Unauthorized" errors gracefully

### ISSUE #3: No Centralized API Error Handling Pattern

**RISK:** LOW  
**LOCATION:** Multiple files (http.ts, CommentsSection.tsx, BettingModal.tsx, etc.)

**Description:**  
API calls are scattered throughout components with inconsistent error handling. Some catch errors, some don't. Some show toasts, some just log. This makes it hard to:
- Ensure all errors are handled safely
- Add global error tracking (e.g., Sentry)
- Implement retry logic
- Handle authentication errors consistently

**Current Pattern:**
```typescript
// CommentsSection.tsx
try {
  const res = await fetch(`${API_URL}/comments?marketId=${marketId}`, {
    credentials: "include",
  });
  if (!res.ok) {
    throw new Error(`Failed to fetch comments: ${res.statusText}`);
  }
  const data = await res.json();
  setComments(data.comments || []);
} catch (err: any) {
  console.error("Error fetching comments:", err);
  setError(err?.message || "Failed to load comments");
}
```

**PATCH:**

Create a centralized API client with safe error handling:

```typescript
// client/web/src/lib/apiClient.ts

import { API_URL } from "./config";
import { sanitizeErrorMessage } from "./errorHandling";

export class APIError extends Error {
  constructor(
    message: string,
    public status: number,
    public data?: any
  ) {
    super(message);
    this.name = "APIError";
  }
}

export interface APIOptions extends RequestInit {
  /** If true, don't throw on non-2xx status codes */
  noThrow?: boolean;
  /** If true, don't include credentials */
  noCredentials?: boolean;
}

/**
 * Safe API client with consistent error handling
 * 
 * Features:
 * - Automatic credential inclusion
 * - Consistent error handling
 * - Type-safe responses
 * - Sanitized error messages
 */
export async function apiClient<T = any>(
  endpoint: string,
  options: APIOptions = {}
): Promise<T> {
  const { noThrow, noCredentials, ...fetchOptions } = options;
  
  const url = endpoint.startsWith("http") ? endpoint : `${API_URL}${endpoint}`;
  
  const config: RequestInit = {
    ...fetchOptions,
    credentials: noCredentials ? "omit" : "include",
    headers: {
      "Content-Type": "application/json",
      ...fetchOptions.headers,
    },
  };
  
  try {
    const response = await fetch(url, config);
    
    // Handle non-2xx responses
    if (!response.ok) {
      let errorData: any;
      try {
        errorData = await response.json();
      } catch {
        errorData = { error: response.statusText };
      }
      
      const errorMessage = errorData?.error || `HTTP ${response.status}`;
      
      if (noThrow) {
        return { error: errorMessage, status: response.status } as any;
      }
      
      throw new APIError(
        sanitizeErrorMessage({ message: errorMessage }),
        response.status,
        errorData
      );
    }
    
    // Parse JSON response
    const data = await response.json();
    return data as T;
    
  } catch (error: any) {
    // Network errors, parse errors, etc.
    if (error instanceof APIError) {
      throw error;
    }
    
    // Wrap other errors
    throw new APIError(
      sanitizeErrorMessage(error),
      0,
      { originalError: error }
    );
  }
}

/**
 * Convenience methods
 */
export const api = {
  get: <T = any>(endpoint: string, options?: APIOptions) =>
    apiClient<T>(endpoint, { ...options, method: "GET" }),
    
  post: <T = any>(endpoint: string, body?: any, options?: APIOptions) =>
    apiClient<T>(endpoint, {
      ...options,
      method: "POST",
      body: body ? JSON.stringify(body) : undefined,
    }),
    
  put: <T = any>(endpoint: string, body?: any, options?: APIOptions) =>
    apiClient<T>(endpoint, {
      ...options,
      method: "PUT",
      body: body ? JSON.stringify(body) : undefined,
    }),
    
  delete: <T = any>(endpoint: string, options?: APIOptions) =>
    apiClient<T>(endpoint, { ...options, method: "DELETE" }),
};
```

**Usage:**

## XSS Vulnerability Analysis

### ✅ No XSS Vulnerabilities Found

**Reason:** React's JSX automatically escapes all interpolated values.

**Example:**
```typescript
// User input: <script>alert('XSS')</script>
const comment = {
  commentText: "<script>alert('XSS')</script>"
};

// Rendered as:
<p>{comment.commentText}</p>

// Output in DOM:
<p>&lt;script&gt;alert('XSS')&lt;/script&gt;</p>
```

**Verified Safe Rendering:**
- ✅ `{comment.commentText}` - Auto-escaped
- ✅ `{comment.username}` - Auto-escaped
- ✅ `{market.displayQuestion}` - Auto-escaped
- ✅ `{outcome.label}` - Auto-escaped
- ✅ `{market.creatorName}` - Auto-escaped

**Only `dangerouslySetInnerHTML` Usage:**
- `chart.tsx` (lines 69-87) - ✅ Safe (CSS generation from config, not user input)

## Wallet Flow Security Review

### Wallet Connection & Signing

**Components Analyzed:**
- `ConnectWalletAndUsername.tsx`
- `BettingModal.tsx`
- `MarketDetails.tsx` (resolve, claim actions)
- `CreateMarket.tsx`

**Security Assessment:**

✅ **GOOD:**
1. **Private keys never leave wallet** - All signing happens in wallet extension
2. **Transaction approval required** - User must approve each transaction
3. **Signature verification on backend** - SIWS flow uses `tweetnacl` to verify signatures
4. **No wallet address spoofing** - Solana wallet adapter provides authenticated `publicKey`

✅ **Authorization Enforced On-Chain:**
- Market resolution: Checked in Anchor program (creator or admin only)
- Claim winnings: Checked in Anchor program (position owner only)
- Place bet: No authorization needed (anyone can bet)
- Create market: No authorization needed (anyone can create, pays fee)

⚠️ **IMPROVEMENT NEEDED:**
- Error messages from failed transactions should be sanitized (see Issue #1)
- UI authorization checks should be clearly marked as UX-only (see Issue #2)
